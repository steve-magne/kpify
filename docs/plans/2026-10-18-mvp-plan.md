# kpify MVP — implementation plan

Status: **proposal, decisions recorded (§6); plan awaiting approval.** Nothing below is built yet.

## 1. Findings that shape the design

- **Packaging.** Current Claude Code convention for a distributable skill set is a
  *plugin*: `.claude-plugin/plugin.json` + `skills/<name>/SKILL.md`, plus a
  `.claude-plugin/marketplace.json` so users install with
  `/plugin marketplace add steve-magne/kpify` → `/plugin install kpify@kpify`.
  Plugin skills are namespaced (`/kpify:define-kpis`). `claude plugin validate .`
  gives us a free structural check. Superpowers (MIT) ships exactly this layout.
  `.claude/skills/` (the brief's proposal) is project-local only — not installable.
- **SKILL.md format.** Frontmatter `name`, `description` (the trigger — the most
  important line), optional `allowed-tools`, `disable-model-invocation`.
  Supporting files live next to SKILL.md; scripts are referenced via
  `${CLAUDE_SKILL_DIR}`. The same `skills/` tree is portable to other agents
  (Agent Skills standard, `npx skills add`).
- **Patterns worth borrowing (ideas, not text):**
  - Superpowers (MIT): an entry skill that forces "check the process first",
    skills as rigid procedures with red-flag/rationalization tables, and
    *baseline-first* skill testing (run the scenario without the skill, record
    failures, then write the skill to fix them).
  - Impeccable (Apache-2.0): one command vocabulary backed by specialist
    reference files; deterministic checks alongside model critique.
  - REA (MIT): evidence workflows — every claim points at an observation.
- **Names.** `kpify` is free on PyPI and npm; GitHub has two empty repos and one
  unrelated 1-star web app. No trademark search done.
- **Local tooling.** Python 3.12 + `uv` present; no pandas/duckdb installed.
  → Tests and fixtures use **Python stdlib only** (`csv`, `sqlite3`, `json`).
  At runtime the agent picks whatever the user's project has, falling back to
  `uv run --with duckdb` / `--with pandas`.

## 2. Workflow and skill boundaries

7 skills for the MVP (brief §12), not 10. `analyze-data` merges into
`validate-metrics` — computing a KPI and checking it are one step with one
artifact. `build-dashboard`, `audit-analysis`, `publish-report` are deferred.

| Skill | Stage | Writes | Gate (stop condition) |
|---|---|---|---|
| `kpify` (entry/router) | — | nothing | Reads `analysis/` to find current stage; routes; enforces order: brief → profile → KPIs → validate → visuals → findings |
| `frame-analysis` | 0 | `01-analysis-brief.md` | Asks ≤3 questions only if an answer changes a KPI or conclusion; otherwise logs assumption |
| `profile-data` | 1 | `02-data-profile.md` | No silent cleaning; every transformation and open DQ issue logged |
| `define-kpis` | 2 | `03-kpi-catalog.md` | Each KPI: formula, num/denom, unit, grain, window, baseline, source cols, caveats — or marked `BLOCKED` |
| `validate-metrics` | 3 | `04-analysis.md`, `kpis.sql`/`.py`, **`kpi-results.json`** | Each KPI has a reproducible calc + named checks (reconcile totals, dedupe, denominators, date bounds); else `UNVALIDATED` |
| `choose-visuals` | 4 | `charts/`, `05-visualization-review.md` | Each chart names its question and its KPI id; review checklist passed |
| `explain-findings` | 5 | `06-executive-summary.md` | Observation / Evidence / Interpretation / Confidence / Next action; no causal claim without design support; "no clear signal" allowed |

Shared material lives once, in `skills/kpify/references/`:
`artifact-templates.md`, `kpi-definition.md` (metric vs KPI vs target vs
dimension), `data-quality-checklist.md`, `chart-selection.md`,
`chart-review-checklist.md`. Stage skills point to these by relative path
(works in a plugin install; single-skill install would lose them — documented).

**Machine-readable contract:** `kpi-results.json` is the one structured output:
`[{id, value, unit, period, segment, status: validated|unvalidated|blocked}]`.
It is what makes runs comparable to known answers.

**Iteration rule:** any skill that invalidates an earlier artifact appends a
`## Revisions` entry there (what changed, why) instead of silently rewriting.

## 3. Acceptance scenario — "Northwind Coffee" (synthetic, known answers)

Small online coffee shop, 6 months (2026-01-01 → 2026-06-14), ~1,500 orders.
Files: `orders.csv`, `order_items.csv`, `customers.csv`.
Generated by a seeded stdlib script; a separate stdlib oracle computes
`expected/kpi-results.json`.

Prompt: *"Here's our shop data. Revenue dropped in June — what happened, and
what should we track monthly?"*

Planted traps (each maps to a brief §8 failure case):

| Trap | Correct behavior |
|---|---|
| June ends on the 14th | Flags incomplete period; compares run-rate or excludes June. The "drop" is mostly an artifact. |
| `order_items` is line-grain | Revenue not double-counted when joined to orders |
| ~2% exact duplicate order rows | Detected, deduped, logged |
| Refunds as negative-amount rows | Gross vs net revenue defined explicitly |
| One B2B order 40× median | Flagged; AOV shown with/without, or median used |
| `promo_code` correlates with higher AOV | Reported as correlation, not cause |
| No traffic/sessions data | Conversion rate marked `BLOCKED` (missing denominator), not invented |

Known answers checked with tolerance: net monthly revenue, orders, AOV, repeat
purchase rate, refund rate (Jan–May full months + June partial flagged).

## 4. Tests

1. `claude plugin validate .` — structure.
2. `tests/check_run.py <analysis-dir> <expected-dir>` (stdlib): required artifacts
   exist with required headings; every KPI in the catalog has all fields;
   `kpi-results.json` matches expected within tolerance; each chart references a
   KPI id; trap checklist via keyword assertions (e.g. "incomplete"/"partial"
   near June, `BLOCKED` on conversion).
3. `tests/run_scenario.sh` — opt-in (costs tokens): copies the fixture to a temp
   dir, runs `claude -p` headless with the plugin, then `check_run.py`.
   Run once **without** the plugin first to record a baseline.

## 5. Increments (one PR each)

1. **Skeleton** — plugin + marketplace manifests, README with install, LICENSE,
   `kpify` router skill, shared reference stubs with artifact templates.
   Done when `claude plugin validate .` passes and `/kpify` routes.
2. **Fixture + oracle + checker** — dataset, expected answers, `check_run.py`,
   baseline run without plugin recorded in `tests/baseline.md`.
3. **frame-analysis + profile-data** — trap rows: duplicates, partial June,
   line grain detected in `02-data-profile.md`.
4. **define-kpis + validate-metrics** — `kpi-results.json` matches oracle.
5. **choose-visuals + explain-findings** — full E2E passes `check_run.py`.
6. **Release v0.1.0** — CHANGELOG, CONTRIBUTING, `docs/methodology.md`,
   `NOTICE` on borrowed ideas.

Deferred (add when MVP passes E2E): `audit-analysis` (reuses the review
checklists), `build-dashboard`, `publish-report`/`07-quality-review.md`,
Evidence output target, SQL database sources, other agent manifests.
